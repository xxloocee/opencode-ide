# Quant Workbench 管理面板完善计划

## 1. 背景与目标

当前 `quant-workbench` 已经具备基础雏形：

- 能识别量化项目工作区
- 能展示策略看板
- 能展示回测详情页
- 能展示数据管理页
- 能从数据管理页发起数据下载

但它目前更像“功能样机”，还不够适合日常管理，主要问题是：

1. 资产之间仍然是分散展示的，缺少“策略 -> 数据 -> 回测结果”的关系组织。
2. 页面能看，但状态不够精细，无法真正支撑管理动作。
3. AI 编排资产、量化业务资产、运行结果资产之间的边界还不够清楚。
4. 下载、扫描、结果刷新虽然打通了基础链路，但还没有形成完整闭环。

本计划的目标不是把 IDE 做成一个通用量化平台，而是把它做成一个**面向本地量化项目的管理控制台**。

这个控制台应服务类似下面这样的真实工作目录：

```text
D:\Project\test-project\quant-test-5-14
  .opencode/
  openspec/
  data/
  momentum_backtest.py
  equity_data.json
  drawdown_data.json
  equity_chart_data.json
  quant.config.json（可选）
```

这里要特别强调：

- `quant.config.json` 不应再被视为默认前提。
- 自动扫描文件夹应该是主路径。
- `quant.config.json` 只作为可选覆盖层，用来修正自动扫描结果，或者在极少数场景下补充运行命令、结果映射等手工定义。

## 2. 真实场景建模

### 2.1 目录角色划分

在这类量化项目里，不同目录承担的职责不同，不应该混在一个层级里管理。

#### A. 主业务资产

这些是管理面板的主对象：

- 策略源码
  - 例如 `momentum_backtest.py`
- 数据资产
  - 例如 `data/*.csv`
  - 例如 `data/raw/*.parquet`
- 回测结果
  - 例如 `equity_data.json`
  - 例如 `drawdown_data.json`
  - 例如 `equity_chart_data.json`
- 运行线索
  - 例如回测命令、输出日志、最近运行记录
  - 这些可以从脚本、运行历史、结果文件推断出来，不强依赖配置文件

#### B. AI 编排与辅助资产

这些对项目重要，但不应该在主工作台里与业务资产平权展示：

- `.opencode/`
- `openspec/`
- `guigu-*`
- `__pycache__/`
- 日志注入文件、上下文文件、模板文件

### 2.2 用户真正想管理什么

面板要回答的不是“这个项目里有什么文件”，而是下面这些管理问题：

1. 现在有哪些策略可以继续开发、继续回测、继续比较？
2. 当前数据覆盖够不够，哪些数据是最新下载的，哪些是模拟数据？
3. 某个策略最近一次回测结果怎么样，是否值得继续迭代？
4. 下载数据、运行回测、查看结果，这三件事能不能形成闭环？
5. AI 辅助生成的 spec / 模板 / 规则，和当前策略有没有直接关系？

## 3. 产品定位

### 3.1 不是“量化平台”

不追求：

- 成为交易终端
- 成为实时盘中监控平台
- 成为分布式回测调度系统
- 成为通用策略研究门户

### 3.2 是“本地量化项目控制台”

追求：

- 在 VS Code / OpenCode IDE 内管理一个具体量化项目
- 围绕“策略、数据、回测结果、运行线索”做管理
- 让 AI 编排资产作为辅助层存在，而不是主资产层
- 让常见动作可以在一个面板里闭环完成

## 4. 信息架构

### 4.1 主导航

建议主导航保持 2 个一级页面：

1. 策略看板
2. 数据管理

其中：

- 回测详情不是独立导航页，而是从策略看板点击某个策略进入的二级详情页
- AI 编排资产不进入主导航

### 4.2 次级入口

辅助入口建议通过以下方式暴露：

- 策略详情页中的“相关脚本 / AI 资产 / 结果来源”折叠区
- 数据页中的“数据来源 / 下载方式 / 文件路径”

### 4.3 资产关系图

```text
策略
  -> 绑定数据资产
  -> 产生回测结果
  -> 关联运行命令与运行历史

数据资产
  -> 按 symbol / market / timeframe / source 组织
  -> 支撑策略回测

回测结果
  -> 归属于策略
  -> 来自一次运行
  -> 对应特定数据范围

AI 编排资产
  -> 辅助策略生成与修改
  -> 不直接作为主导航资产
```

## 5. 页面设计要求

### 5.1 策略看板

目标：成为“策略资产清单”。

页面应包含：

- 顶部摘要条
  - 总策略数
  - 已回测数量
  - 平均夏普
  - 最佳收益策略
- 状态筛选
  - 全部 / 草稿 / 已回测 / 运行中 / 实盘中 / 已归档
- 资产筛选
  - 全部 / 现货 / 合约 / 期权
- 排序
  - 最近更新 / 收益率 / 夏普比率
- 策略列表
  - 策略名
  - 状态
  - 标的或市场标签
  - 版本数
  - 最近收益率
  - 夏普比率
  - 最近日期

点击某个策略，应直接进入该策略的回测详情。

### 5.2 回测详情

目标：成为“策略结果页”，而不是通用详情页。

页面应包含：

- 面包屑
  - 策略看板 / 策略名
- 标题区
  - 策略名
  - 状态
  - 标的标签
  - 版本信息
- 左侧主区
  - Equity Curve
  - Drawdown
- 右侧指标卡
  - 总收益率
  - 夏普比率
  - 最大回撤
  - 总交易数
- 元信息区
  - 日期范围
  - 结果文件
  - 运行命令
  - 入口文件
- 关联数据区
  - 展示与当前策略匹配的数据资产
  - 展示绑定解释

后续增强项：

- 历史回测快照列表
- 参数版本比较
- 结果来源快照

### 5.3 数据管理

目标：成为“数据资产仓库”。

页面应包含：

- 顶部摘要条
  - 文件数
  - 总大小
  - 标的数
  - 覆盖范围
  - 下载任务状态
- 筛选条
  - 市场：全部 / 现货 / 合约 / 期权
  - 粒度：全部 / 1d / 4h / 1h / 30m / 15m / 5m / 1m
- 分组列表
  - 按 `symbol + market` 分组
  - 每组显示文件数
  - 支持展开/折叠
- 文件行信息
  - 文件名
  - 时间范围或覆盖范围
  - 粒度
  - 数据类型
  - 状态
  - 来源维度：真实 / 模拟
  - 形态维度：主数据 / 缓存分片 / partial

下载后的新文件应该能自动刷新并显示出来。

### 5.4 数据下载弹窗

目标：成为“下载任务创建器”。

弹窗应包含：

- 下载渠道
  - 自动（推荐）
  - 真实数据
  - 模拟数据
- 交易所
  - binance
  - okx
  - bybit
  - noexchange（仅模拟）
- 标的
  - 例如 `BTC/USDT`
  - 合约场景需要可扩展为 `BTC/USDT:USDT`
- 市场
  - 现货 / 合约 / 期权
- 数据类型
  - `ohlcv`
  - `trades`
  - `funding_rate`
  - `open_interest`
  - `book_l1`
  - `book_l2`
  - `liquidations`
- 时间粒度
  - `1m / 5m / 15m / 30m / 1h / 4h / 1d`
- 开始日期
- 结束日期

要求：

- 使用日期选择器，而不是纯文本输入
- 表单必须做基础校验
- 参数不合法时不允许提交

## 6. 与现有 Python 下载链路的集成要求

### 6.1 当前真实链路

`quant-test-5-14` 中的数据下载不是通过独立脚本手工跑的，而是通过：

```bash
python -m guigu_data crypto get <symbol> <start> <end> [options]
```

该命令位于：

```text
.opencode/pythonlib/guigu_data
```

### 6.2 扩展执行方式

扩展点击“开始下载”时，应由扩展后端执行 Python 命令，而不是前端直接处理。

执行要求：

- `cwd` 必须是当前量化项目根目录
- `PYTHONPATH` 必须包含 `.opencode/pythonlib`
- 命令通过扩展侧执行，并写入 Output Channel

### 6.3 下载渠道映射

建议映射规则：

- 自动
  - 使用用户选择的交易所
  - 由 `guigu_data` 自己决定是否回退模拟数据
- 真实数据
  - 当前先限制到真实支持明确的交易所
  - 第一阶段建议只保证 `binance`
- 模拟数据
  - 强制使用 `noexchange`
  - 或显式引导到模拟器路径

### 6.4 下载完成后的闭环

成功下载后，应自动做 3 件事：

1. 刷新数据扫描
2. 刷新侧边栏数据视图
3. 若当前在数据管理页，自动刷新页面内容

## 7. 扫描与索引策略

### 7.1 策略扫描

第一阶段支持（全部基于自动扫描文件夹）：

- 根目录及子目录下 `*_backtest.py` 文件

后续增强：

- 同一策略多版本识别（文件名中的版本号或时间戳）
- 将 `*_strategy.py` 作为候选策略脚本识别，但不默认进入主策略清单
- 基于 spec / 模板的策略来源识别

### 7.2 数据扫描

当前需要支持：

- `data/*.csv`
- `data/**/*.parquet`
- `data/raw/*.parquet`

后续增强：

- 自动识别真实 / 模拟文件
- 从文件名解析 symbol / dtype / interval / start / end（best-effort，解析失败时显示“未知”标签）
- 同标的多粒度聚合

#### 文件命名解析规则

文件名解析采用 best-effort 策略，尽可能覆盖常见命名约定，不强制要求统一格式。

识别时按优先级尝试以下模式：

```text
模式 1（guigu_data 原始缓存，优先支持）：
  {exchange}-{symbol}-{dtype}-{interval}-{start}-{end}.parquet
  {exchange}-{symbol}-{dtype}-{interval}-{start}-{end}.partial.parquet
  例：binance-ETH-USDT-ohlcv-1d-2026-02-01-2026-02-28.parquet
  例：binance-ETH-USDT-ohlcv-1d-2026-05-01-2026-05-31.partial.parquet

模式 2（结构化命名）：
  {symbol}_{market}_{dtype}_{interval}_{start}_{end}.{ext}
  例：BTC_USDT_ohlcv_1d_20240101_20241231.parquet
  例：ETH_USDT_trades_1h_20240601_20240701.csv

模式 3（简化命名）：
  {symbol}_{dtype}_{interval}.{ext}
  例：BTC_ohlcv_1d.csv
  例：ETH_trades_1h.parquet

模式 4（仅 symbol）：
  {symbol}.{ext}
  例：BTC.csv
  例：ETH.parquet

模式 5（无结构信息）：
  无法解析出 symbol 等字段时，仅展示文件名、大小、修改时间
  标签显示为“未识别”
```

解析时需注意：

- symbol 中的 `/` 可能被替换为 `_` 或 `-`
- market 可能是 `spot`、`futures`、`perp`、`usdt` 等多种变体，需要做归一化映射
- `ohlcv` / `kline` / `candle` 视为同一数据类型
- interval 中的 `1D` / `1d` / `daily` 视为同一粒度
- `.partial.parquet` 代表当前月份或未完整下载的缓存分片，需单独标识

无法匹配任何模式时，不报错，仅以文件名 + 大小 + 修改时间展示。

### 7.3 回测结果扫描

第一阶段支持（基于规则匹配，不硬编码单一文件名）：

识别根目录及子目录下的 JSON 文件，通过以下特征判定是否为回测结果：

```text
匹配规则：
  1. 文件内容包含 equity / equity_curve / portfolio_value 等关键字段
  2. 文件内容包含 drawdown / max_drawdown 等关键字段
  3. 文件名中包含 equity / drawdown / result / backtest 等关键词
```

优先级：

- 内容特征匹配 > 文件名匹配
- 两者都不匹配的 JSON 文件不纳入回测结果

后续增强：

- 多次回测结果归档
- 历史结果索引
- 快照式结果比较

## 8. AI 编排资产的处理原则

### 8.1 原则

`.opencode/` 和 `openspec/` 不是不要，而是不要与主业务资产平权展示。

### 8.2 建议处理方式

第一阶段：

- 不进入主导航
- 不进入主列表
- 只在策略详情页中提供只读入口

第二阶段：

- 针对当前策略显示“相关 spec / 模板 / AI 生成痕迹”
- 提供跳转到对应文件的快捷操作

第三阶段：

- 再评估是否需要独立“AI 资产”页

## 9. 当前实现与目标之间的缺口

### 9.1 已经具备

- 项目识别
- 策略看板基础布局
- 回测详情基础页面
- 数据管理基础页面
- 数据下载表单和基础命令执行

### 9.2 还缺少

#### A. 关系绑定

- 策略与数据资产的明确绑定
- 策略与回测结果的历史关联
- 下载任务与数据资产的状态关联

#### B. 状态精细化

- 下载中 / 已完成 / 失败 / 模拟
- 回测成功 / 失败 / 结果未刷新
- 数据覆盖是否满足策略要求

#### C. 管理动作闭环

- 下载后自动看到新数据
- 回测后自动更新结果页
- 从结果页反查使用了哪些数据

#### D. 资产分层

- AI 编排资产和业务资产分层不够清楚

#### E. 错误与异常处理

- 下载失败、Python 命令执行错误的展示与重试
- 文件扫描异常（文件损坏、读取失败）的容错处理
- 未知文件名格式的降级展示

## 10. 分阶段实施计划

### 阶段 1：数据下载闭环

目标：

- Python 下载命令真实可执行
- 下载后数据页能看到新文件
- 下载异常有清晰的错误展示

交付项：

- 下载弹窗基础表单（交易所、标的、市场、数据类型、时间粒度、日期范围）
- 日期选择器
- 表单基础校验
- Output Channel 日志输出
- 下载失败与环境异常状态展示
- `parquet` 扫描支持
- 下载成功后自动刷新

验收标准：

- 可以从数据管理页下载真实或模拟数据
- 下载完成后无需手工刷新即可在数据页看到新资产
- 下载失败时能看到明确错误原因和重试入口

### 阶段 2：数据资产精细化

目标：

- 把“文件列表”升级成“数据资产视图”

交付项：

- 来源维度标签：真实 / 模拟
- 形态维度标签：主数据 / 缓存分片 / partial
- 按 `symbol + market` 分组
- 文件名结构化解析（优先支持 `guigu_data` 生成的 raw parquet 命名）
- 覆盖范围聚合
- 解析失败时的降级展示

验收标准：

- 用户可以直接判断某个标的有哪些可用数据
- 能区分真实数据和模拟数据
- 能区分主数据和缓存分片

### 阶段 3：策略与数据绑定

目标：

- 面板真正进入“管理”而不是“展示”

交付项：

- 从策略文件名和内容中推断默认 symbol / market / timeframe（best-effort，不依赖配置文件）
- 在策略详情页展示关联数据
- 从数据页反向跳转到相关策略
- 源码不存在时的降级展示

验收标准：

- 打开一个策略时，可以直接知道它对应的数据资产
- 自动绑定失败时不阻断其他功能

### 阶段 4：回测结果管理

目标：

- 从“看一次结果”升级成“管理结果历史”

交付项：

- 回测结果快照
- 最近回测历史
- 结果文件归档
- 结果状态刷新

验收标准：

- 同一策略多次回测结果可追踪、可比较

### 阶段 5：AI 资产只读接入

目标：

- 让 AI 编排层可见，但不打乱主面板

交付项：

- 策略详情页中的相关 spec / 模板入口
- 配置与编排文件的只读跳转

验收标准：

- 用户能定位 AI 辅助资产，但主工作流仍然围绕策略 / 数据 / 回测

## 11. 非目标

当前不做：

- 实盘交易终端
- 实时行情面板
- 多项目统一投资组合视图
- 分布式回测任务队列
- 参数网格搜索系统
- 把 `.opencode` / `openspec` 变成主工作台一级页面

## 12. 建议的下一步

如果按投入产出比排序，推荐顺序是：

1. 继续把“下载任务状态”做完整
2. 做数据文件名结构化解析
3. 做策略与数据绑定关系
4. 做回测结果历史管理
5. 最后再补 AI 编排资产入口

原因很简单：

- 先让面板形成闭环
- 再让面板变得精细
- 最后才补辅助层入口

这样做，面板会先变得“能管理”，再变得“更聪明”。
