# 分支同步与开发流程

本文档说明当前仓库采用的单主线分支策略，以及日常开发和同步上游时应该怎么操作。

## 目标

这个仓库同时要满足两件事：

1. 持续跟进上游 `microsoft/vscode` 的最新 `main` 分支。
2. 保留我们自己的改动，并且让开发流程尽量简单、可控。

这里的核心取舍是：在“只有一个人长期开发”的前提下，不再为了流程完整性维护多条长期分支，而是把复杂度压到最低。

- 少一层分支，就少一层同步、rebase、merge 和冲突入口。
- 日常开发、验证和发布都围绕 `main` 进行，心智负担更低。
- 只有在确实需要吸收上游时，才在 `main` 上处理一次明确的同步动作。

## 分支职责

### `main`

- 这是唯一长期维护的工作分支。
- 日常开发、修复、实验性修改、验证后的提交，都直接落在 `main`。
- 它既是默认分支，也是对外可见的主线历史。
- 当需要同步上游时，也直接在这个分支上完成，不再额外维护 `dev` 或 `sync-main`。

## 远端约定

- `origin`：当前私有仓库。
- `upstream`：官方上游仓库 `https://github.com/microsoft/vscode.git`。

## 上游同步机制

当前仓库不再维护专门的上游同步分支，也不依赖额外 workflow 去帮我们兜这一层。

原因是：

1. 单人开发场景下，多一条长期同步分支并不会带来真实收益。
2. `dev` / `sync-main` 会把一次简单同步拆成多次分支切换、rebase 和历史维护。
3. 真正需要处理的复杂度其实只有一个：把自己的 `main` 跟上 `upstream/main`。

因此这里改成直接在 `main` 上手动同步：

1. 获取最新 `upstream/main`。
2. 在 `main` 上把自己的提交 rebase 到最新上游之上。
3. 解决冲突并验证结果。
4. 确认无误后，把更新后的 `main` 推回 `origin`。

这样流程里只保留一条真正需要维护的主线，出问题时也只需要围绕 `main` 排查。

## 日常开发流程

### 开始开发

```bash
git checkout main
git fetch origin
git pull --ff-only origin main
```

拉到最新后，直接在 `main` 上开发、提交、测试即可。

### 同步最新上游基线

需要吸收上游改动时，直接在 `main` 上处理：

```bash
git checkout main
git fetch upstream
git rebase upstream/main
```

如果 rebase 过程中发生冲突，就在 `main` 上直接解决，然后继续：

```bash
git rebase --continue
```

rebase 完成并验证通过后，再把改写后的主线推回远端：

```bash
git push --force-with-lease origin main
```

如果这次并不是同步上游，而只是推送自己的日常开发提交，正常使用下面这条就够了：

```bash
git push origin main
```

## 提交流程建议

推荐顺序：

1. 开始前先把本地 `main` 同步到 `origin/main`。
2. 所有日常改动直接提交到 `main`。
3. 需要吸收上游时，再把 `main` rebase 到 `upstream/main`。
4. 在 `main` 上解决冲突、验证结果。
5. 完成后把 `main` 推回 `origin`。

## GitHub 仓库设置建议

- 默认分支建议设为 `main`。
- 日常开发直接使用 `main`。

## 为什么不再维护 `dev` 和 `sync-main`

过去保留多条长期分支，本质上是在为“多人并行协作”和“同步层 / 集成层拆分”付管理成本。但在当前仓库里，这个成本已经高于收益：

1. 这里只有一个长期开发者，不存在多人先汇总到 `dev` 再统一进 `main` 的协作收益。
2. 每多一条长期分支，就多一套同步关系、多一个冲突入口、多一层历史维护。
3. 真正需要保留的边界只有一个：`main` 既承接自己的开发，也承接上游同步后的结果。

所以这里保留的最小必要流程就是：

- 日常开发直接在 `main`
- 需要跟进上游时，在 `main` 上执行一次明确的 rebase
- 验证通过后，把 `main` 推回远端

分支越少，流程越短，认知负担越低。对当前这个仓库来说，这就是最划算的做法。
